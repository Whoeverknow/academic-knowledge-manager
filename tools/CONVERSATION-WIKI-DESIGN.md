# 会话 Wiki 编目系统：跨会话上下文继承设计

> 附录于 `tools/SYSTEM-DESIGN-v3.0.md`
> 基于 2026-05-30 讨论：当新会话需要继承旧会话上下文，但完整 Transcript 会爆上下文时，如何用 LLM Wiki 的树形目录思想解决。
> 本章先枚举 50 个场景建立需求全景，再做系统设计。

## A.2 场景分析的关键发现

审核 50 个场景后，一个规律非常清晰：

> **在 50 个场景中，只有场景 C17 和 C18 需要访问对话正文（"精准定位那一段"）。其他 48 个场景只需要：会话 ID + 话题标签 + 结论摘要 + KNID 引用 + 未决问题列表。**

这意味着：如果每个会话在结束时生成一个 **~200-500 token 的结构化节点**（而非保留 20K-100K token 的完整 Transcript），新会话的上下文继承就可以做到"48/50 的场景覆盖"，而只消耗 <1% 的 token 预算。

## A.3 会话 Wiki 架构设计

### A.3.1 核心思想

将 LLM Wiki 的树形目录结构应用于会话管理：

- **每个会话 = 一个 Wiki 页面节点**（轻量，只含元数据和摘要）
- **活跃线程 = Wiki 的 Category/Portal 页面**（聚合跨会话的主题讨论）
- **完整 Transcript = 冷存储**（可访问但从不预加载）
- **会话节点之间的链接 = Wiki 的交叉引用**（Related、Parent、Child、FollowUp）

### A.3.2 目录结构

```
conversations/                       # 新增：会话 Wiki 编目
├── INDEX.md                         # 会话注册表（启动时加载，<2K tokens）
├── nodes/                           # 会话节点（每个会话一个文件，~200-500 tokens）
│   ├── 2026/
│   │   ├── 05/
│   │   │   ├── 2026-05-27-knowledge-extraction.md
│   │   │   ├── 2026-05-28-philosophy-system-design.md
│   │   │   ├── 2026-05-30-architecture-redesign.md
│   │   │   └── ...
│   │   └── 06/
│   └── ...
├── threads/                         # 活跃线程（跨会话主题聚合器）
│   ├── ecology-economy-modeling.md  # 生态-经济建模讨论的完整脉络
│   ├── knowledge-system-design.md   # 知识系统本身的架构讨论
│   ├── philosophical-foundations.md # 哲学/思辨性讨论
│   └── ...
├── transcripts/                     # 完整 Transcript 冷存储
│   ├── 2026/
│   │   ├── 05/
│   │   │   ├── 2026-05-27-full.md
│   │   │   └── ...
│   └── ...
└── ARCHIVE.md                       # 退役/合并的会话节点索引
```

### A.3.3 会话节点的标准格式

每个会话结束时，生成一个结构化节点文件。这个文件是"会话的 Wiki 页面"：

```markdown
### SESSION-2026-05-30-001 | 系统架构重设计与会话 Wiki 设计

**日期**: 2026-05-30 | **持续时间**: ~4h
**状态**: #active | **类型**: #design #philosophy #system-architecture
**窗口角色**: 系统架构设计（主窗口）

## 话题标签
`#system-architecture` `#context-budget` `#skill-design` `#conversation-wiki` `#zipf-law`

## 摘要
讨论从 academic-knowledge-manager SKILL.md 膨胀出发，诊断出系统级上下文预算问题。引入 steipete 元原则（上下文即成本、原子解耦）、齐夫定律（排名驱动降冷而非时间驱动）、文献半衰期（不同类型知识的衰减系数）。设计了 SKILL.md 三向拆分方案和会话 Wiki 编目系统。

## 关键结论
1. 降冷不应基于固定时间阈值，应基于齐夫排名 + 半衰期衰减系数
2. 检索应走 Wiki 链接导航（Related+Tags+Graph），而非外挂搜索引擎
3. 启动集应只含 Skill 注册表，完整指令在调用时展开
4. 跨会话继承通过会话 Wiki 节点实现，不加载完整 Transcript

## 创建的 KNID
_（本次讨论为系统设计元讨论，暂未创建新的知识条目）_

## 未决问题
1. STRATEGY.md 是否允许从使用中自动调整？
2. Skill 原子化应该推进到多细的粒度？
3. 跨 session transcript 检索的最优方案？
4. 会话 Wiki 节点的生成时机——会话结束时由 Steward 自动生成？还是由 Scholar 确认后生成？

## 关联
- **父会话**: SESSION-2026-05-28-001（系统架构讨论的起点）
- **子会话**: _（尚无）_
- **相关会话**: SESSION-2026-05-27-001（知识库初始创建，本会话的理论基础）
- **活跃线程**: [[knowledge-system-design]]

## 系统状态变更
- 修订了 `tools/SYSTEM-DESIGN-v3.0.md`（新增 Chapter 7）
- 暂无 constitution amendment

---
```

### A.3.4 活跃线程的格式

线程是"横切"会话的聚合页面——一个线程对应一个长期讨论主题：

```markdown
# Thread: knowledge-system-design

**创建**: 2026-05-28 | **最后更新**: 2026-05-30
**状态**: #active | **会话数**: 3

## 脉络

1. **SESSION-2026-05-28-001** — 初始诊断：SKILL.md 膨胀与上下文预算危机
   - 识别了三合一问题（宪法/工作流/策略）
   - 提出了五项设计原则
   
2. **SESSION-2026-05-30-001** — 深化设计：积分半衰期 + Wiki 导航 + 会话编目
   - 引入 steipete 元原则、齐夫定律降冷、文献半衰期
   - 设计了会话 Wiki 编目系统
   - 50 个跨会话场景的系统分析

3. _（下一个会话将在此处续接）_

## 累积的关键结论
- [ ] SKILL.md 三向拆分方案已确定，待执行
- [ ] 会话 Wiki 节点格式已定义，待 Scholar 确认
- [ ] 降冷机制从时间驱动改为排名驱动，已共识

## 累积的未决问题
- STRATEGY.md 的自动调整权限
- Skill 原子化粒度
```

### A.3.5 新会话的启动协议

当一个新会话启动时，它需要回答"我在哪、我们之前做了什么"——但不超过 ~5K tokens：

```
Step 1: 加载 conversations/INDEX.md (~2K tokens, 所有会话的注册表)
         → 获取：活跃会话列表、最近 N 个会话标题、活跃线程列表

Step 2: 检查活跃线程，加载所有活跃线程的摘要行 (~1K tokens)
         → 获取：跨会话的持续讨论主题

Step 3: 如果 Scholar 的第一个输入是"继续"或类似的续接信号
         → 定位最近的活跃会话 → 加载该会话节点 (~500 tokens)
         → 不加载完整 Transcript

Step 4: 如果 Scholar 引用特定的历史会话
         → 加载该会话节点 (~500 tokens)
         → 如果需要正文内容（场景 C17/C18），精准加载 Transcript 的相关段落

Step 5: 如果 Scholar 没有特别指向历史
         → 只保留 INDEX.md + 线程索引
         → 作为一个"fresh but aware"的会话开始
```

**关键约束**：
- **永不预加载任何完整 Transcript。** Transcript 是冷存储，只在 Scholar 显式要求时、且只加载相关段落时才访问。
- **永不预加载不活跃的会话节点。** 会话节点的加载遵循与知识条目相同的齐夫排名原则：最近访问的、被活跃线程引用的会话保持在"热节点"中；其他会话在 INDEX.md 中只有一行。

### A.3.6 会话节点与知识条目的双向溯源

```
会话节点                         知识条目
┌──────────────────┐           ┌──────────────────┐
│ SESSION-X        │           │ KNID-Y           │
│                  │           │                  │
│ 创建的 KNID:     │──────────→│ 来源会话:        │
│   - KNID-Y       │           │   - SESSION-X    │
│   - KNID-Z       │           │                  │
└──────────────────┘           └──────────────────┘
         ↑                            │
         └────────────────────────────┘
              双向引用，各自在节点中只存一行
```

- 知识条目中：`**Sources**: └ [Conversation] SESSION-2026-05-27-001`
- 会话节点中：`## 创建的 KNID: - KNID-Y（标题）`

双向链接的总成本：每个方向 <50 tokens。但它的收益是：从知识条目可以跳回产生它的对话，从对话可以找到它产出了什么知识。

## A.4 与现有架构的集成

### A.4.1 在四目录结构中的位置

当前架构：
```
/
├── tools/          # 管理基础设施
├── work/           # 未发布的草稿
├── knowledge/      # 已发布的知识条目
└── baseline/       # 版本化存档
```

新增：
```
/
├── tools/
├── work/
├── knowledge/
├── baseline/
└── conversations/  # 新增：会话 Wiki 编目
    ├── INDEX.md
    ├── nodes/
    ├── threads/
    ├── transcripts/
    └── ARCHIVE.md
```

**为什么 `conversations/` 应该是一级目录？**

因为它不是知识（knowledge/），不是草稿（work/），不是管理工具（tools/），也不是规则存档（baseline/）。它是一个新的本体类别：**过程的编目**。它横切了所有其他目录——一个会话可能讨论知识条目、修改管理规则、产生哲学洞察——但它本身不是这些中的任何一个。

### A.4.2 预算分配

| 子系统 | 启动时加载 | 按需加载 |
|--------|----------|---------|
| 会话 Wiki | INDEX.md (~2K tokens) + 活跃线程标题 | 单会话节点 (~500 tokens) / 线程全文 |
| 知识库 | — | INDEX.md / 单个条目 |
| Skill 系统 | Skill 注册表 | 被调用的 Skill 的完整指令 |
| 记忆系统 | 记忆索引 | 具体记忆文件 |
| 完整 Transcript | **永不预加载** | 仅在 Scholar 要求时、仅相关段落 |

### A.4.3 会话节点的生成与维护

**生成时机**：每个会话结束时，由 Steward 自动生成会话节点草稿，写入 `conversations/nodes/`。节点中的"未决问题"和"关键结论"部分应提请 Scholar 确认（因为这些是跨会话继承的核心内容）。

**维护任务**（列入每日/每周维护计划）：
- 日检：检查 INDEX.md 是否有新会话未注册 → 注册
- 周检：检查是否有没有后续的悬置线程 → 标记 `#dangling`；检查是否有可以合并的重复节点；更新活跃线程的累积结论

**ARCHIVE.md**：当一个会话节点因为含义被更高层级的线程节点覆盖而不再独立有用时——例如，五个关于同一主题的短会话被聚合为一个线程节点——单个会话节点可以被降冷到 ARCHIVE.md（类似墓碑，保留标题和链接但不再占用热索引空间）。

| 场景类别 | 数量 | 需要加载的内容 | Token 估算 |
|---------|------|-------------|-----------|
| A 类：同主题续接 | 10 | 最近会话节点 + 线程节点 | ~1K |
