# 记忆 Wiki 编目系统设计

> 配套于 `tools/SYSTEM-DESIGN-v3.0.md` 和 `tools/CONVERSATION-WIKI-DESIGN.md`
> 基于 2026-05-30 讨论：记忆文件终身积累，即使每个记忆文件很小，启动时全部加载的复利效应会蚕食上下文预算
> 核心问题：当前的 MEMORY.md 是扁平索引——每条记忆一行，全部加载——没有生命周期、没有冷热分层、没有主题线程序列化

---

## B.1 问题诊断

### B.1.1 记忆与 Transcript 的同构性

对话 Transcript 和记忆文件表面上是两类东西，但在"上下文预算"的视角下，它们是同构的：

| 维度 | Transcript | 记忆 |
|------|-----------|------|
| 增长模式 | 每次会话 +1 | 每次值得记住的事件 +1 |
| 规模趋势 | 随会话数线性增长 | 随使用时间线性增长 |
| 每条大小 | 大（20K-100K tokens） | 小（200-2000 tokens） |
| 启动时加载 | 否（已解决：不预加载） | **是——这是问题** |
| 有冷热分层？ | ✓（会话 Wiki 节点/线程/Transcript 三级） | **否——这是问题** |
| 有过期机制？ | ✓（自然的：旧会话不活跃自然下沉） | **否——这是问题** |

当前 20 条记忆时，全量加载 MEMORY.md + 所有记忆文件不是问题。但终身积累意味着：
- 第 1 年：~50 条记忆，~10K tokens → 可以接受
- 第 3 年：~150 条记忆，~30K tokens → 开始侵蚀
- 第 5 年：~250 条记忆，~50K tokens → 严重影响

### B.1.2 当前记忆系统的"死"

当前的记忆系统虽然没有冷热分层，但它其实已经有了自然的"死"——只是没有被系统识别：

- 一个 2024 年的项目记忆，该项目已完成，之后从未被提及 → **隐性死**
- 一个关于某工具偏好的反馈记忆，该工具已不再使用 → **隐性死**
- 一条"不要截断帮我保留上下文"的反馈——在系统已经采纳为默认行为后，这条记忆是冗余的 → **隐性死**
- 一个指向已不存在的 Slack 频道的 reference 记忆 → **隐性死**

问题不是没有死——而是**系统无法区分谁活着、谁死了**。当前的 MEMORY.md 是一个没有墓碑的墓地。

### B.1.3 为什么空行清理不够

当前系统的维护逻辑隐含了一个假设：文件多了 → 清理一下 → 就好了。但记忆的膨胀不是"多余"的问题——每条记忆在创建时都是合理的。问题是**有些记忆的"合理性"随时间衰减了**，而系统没有机制表达这个衰减。

---

## B.2 记忆的齐夫分布

记忆的访问模式和知识条目一样，服从幂律：

- **热记忆（前 20%）**：用户偏好、当前项目的关键信息、刚写入的反馈 → 每次会话都被引用
- **温记忆（中间 40%）**：偶尔相关的项目记录、一般性的偏好 → 每几次会话引用一次
- **冷记忆（后 40%）**：已完成的项目、过时的参考、已被吸收的反馈 → 几乎不再引用

关键洞察：40% 的记忆可能承载不到 5% 的访问需求，但在当前架构下，它们和热记忆一样，每次都进入上下文。

## B.3 记忆 Wiki 架构设计

### B.3.1 核心原则

与对话 Wiki 一致，但更轻量（因为单条记忆本身就比单场对话小得多）：

- **MEMORY.md 从"全量索引"降级为"热索引注册表"**（启动时加载，<2K tokens）
- **单个记忆文件保持原位**，但按需加载——只在当前对话明显需要时才读入
- **新增 `memory/archive/`**：降冷的记忆
- **新增记忆线程**：横切多个记忆文件的主题线

### B.3.2 目录结构

```
memory/
├── MEMORY.md                       # 热索引注册表（启动时加载，~2K tokens）
│                                   # 每行格式变更：
│                                   # - [Title](file.md) — hook | #tag1 #tag2 | active:YYYY-MM-DD | N refs
│
├── user/                           # 用户相关记忆（文件原位不变）
│   ├── role.md
│   ├── preferences.md
│   └── ...
├── feedback/                       # 反馈相关记忆
│   ├── context-preservation.md
│   └── ...
├── project/                        # 项目相关记忆
│   ├── ecology-economy-modeling-research-thread.md
│   └── ...
├── reference/                      # 引用相关记忆
│   └── ...
│
├── threads/                        # 新增：记忆线程（跨文件主题聚合）
│   ├── research-workflow.md        # "研究流程偏好"线程
│   ├── writing-style.md            # "写作风格"线程
│   └── ...
│
├── archive/                        # 新增：降冷记忆
│   ├── INDEX.md                    # 冷记忆注册表
│   └── ...
│
└── audit/                          # 新增：记忆变更审计日志
    └── memory-audit.log
```

### B.3.3 MEMORY.md 的新格式

当前格式：
```
- [Academic Knowledge Manager](academic-knowledge-manager.md) — 个人学术知识管理体系
```

新格式（增加生命周期元数据，全在一行内）：
```
- [Academic Knowledge Manager](academic-knowledge-manager.md) — 个人学术知识管理体系 | #knowledge-system #active | active:2026-05-27 | refs:12 | τ:0.001
```

| 字段 | 含义 | 何时更新 |
|------|------|---------|
| `#tags` | 记忆的主题标签 | 创建时分配，可修订 |
| `#active / #warm / #cold` | 记忆的热度状态 | 自动（基于引用排名） |
| `active:YYYY-MM-DD` | 最近一次被引用的日期 | 每次引用时自动更新 |
| `refs:N` | 历史总引用次数 | 每次引用时自动更新 |
| `τ:value` | 半衰期衰减系数（越小越慢衰减） | 创建时按类型分配，可修订 |

### B.3.4 单个记忆文件的格式增强

每个记忆文件保持其现有关键内容不变，但增加标准化的元数据字段——这些字段很小（<100 tokens），但提供了生命周期管理所需的全部信息：

```markdown
---
name: {{name}}
description: {{one-line}}
type: {{user/feedback/project/reference}}
tags: [{{tag1}}, {{tag2}}]
created: {{YYYY-MM-DD}}
last_referenced: {{YYYY-MM-DD}}
reference_count: {{N}}
half_life_factor: {{τ}}
status: {{active/warm/cold}}
thread: {{thread-name}}  # 可选，所属的记忆线程
related_sessions: [{{SESSION-ID}}]  # 可选，产生此记忆的会话
---

{{现有内容不变}}
```

这些元数据字段的总成本 <100 tokens/条。但它们让每一条记忆对自己的生命周期有了自我意识。

### B.3.5 记忆线程

记忆线程是记忆 Wiki 的"横切"层——类似对话 Wiki 中的活跃线程。一条记忆线程聚合了分散在不同文件中的相关记忆：

```
# Thread: research-workflow

**描述**: 关于研究流程的工具偏好、方法选择、工作习惯

**包含的记忆**:
- feedback/context-preservation.md — "保留完整上下文"偏好
- user/preferences.md — Python + 数据科学技术栈偏好
- feedback/memory-usage-pattern.md — 记忆使用习惯的反馈
- reference/knowledge-base-location.md — 知识库路径引用

**状态**: #active | 最后更新: 2026-05-30
```

线程的价值：当 Scholar 在新会话中说"按照我的研究习惯来做"，系统不需要加载所有 250 条记忆——只需要加载"研究流程"线程下的 4-5 条热记忆。

### B.3.6 记忆的生命周期（齐夫定律 + 半衰期）

与知识条目相同的模型，但参数更积极（记忆通常比知识条目衰减更快）：

| 记忆类型 | τ 系数 | 原因 |
|---------|--------|------|
| **user**（角色/偏好） | **0.001**（极慢） | 用户的基本角色和偏好变化很慢 |
| **feedback**（工作风格反馈） | **0.005**（慢） | 一旦形成的工作风格会持续很久，但可能被更新的反馈覆盖 |
| **project**（项目进展） | **0.02**（中） | 项目有生命周期；完成后快速衰减 |
| **reference**（外部引用） | **0.03**（较快） | 外部资源的位置和状态变化快 |

**状态转换**（排名驱动，非时间驱动）：

```
热记忆（active）
  │
  │ 引用排名跌出 K_hot（热记忆容量）→ 但仍在前 K_warm
  ▼
温记忆（warm）—— 文件名仍在 MEMORY.md 中，但标记 #warm
  │
  │ 继续下跌 → 跌出 K_warm
  ▼
冷记忆（cold）—— 从 MEMORY.md 移除，移入 archive/INDEX.md
  │
  │ Scholar 显式引用 → 复活（重新进入热索引）
  ▼
  ▲  或继续衰减 → 365 天无引用 → 可以考虑真正的退役
```

**关键参数**：

| 参数 | 含义 | 建议值 |
|------|------|--------|
| $K_\text{hot}$ | 热记忆容量 | ~20-30 条 |
| $K_\text{warm}$ | 温记忆容量（热+温） | ~60-80 条 |
| 热→温过渡 | 触发条件 | 修正排名跌出 $K_\text{hot}$ |
| 温→冷过渡 | 触发条件 | 修正排名跌出 $K_\text{warm}$ |
| 冷→退役 | 触发条件 | 连续 365 天无引用 |

## B.4 新会话的启动协议（含记忆）

修订后的启动协议，将记忆子系统纳入：

```
Step 1: 加载 conversations/INDEX.md          (~2K tokens)
Step 2: 加载 MEMORY.md（热+温记忆注册表）      (~2K tokens)  ← 变更
Step 3: 加载 Skill 注册表                      (~1K tokens)
Step 4: 加载活跃线程索引（会话 + 记忆）         (~1K tokens)
                                             ─────────────
启动集总计                                      ~6K tokens
```

**不加载的内容**（除非当前对话需要）：
- 任何记忆文件的正文
- 任何会话节点的正文
- 任何 Skill 的完整指令
- 任何冷记忆的注册表

**按需加载的触发条件**：
- Scholar 提到某个具体主题 → 搜索 MEMORY.md 中的标签 → 加载相关记忆的正文
- Scholar 说"按我的偏好来做" → 加载用户记忆线程下的热记忆
- Scholar 说"上次那个项目…" → 搜索项目标签 → 加载匹配的记忆

## B.5 记忆与对话 Wiki 的双向链接

记忆和对话 Wiki 之间存在自然的关系——大多数记忆是从对话中产生的：

```
会话 Wiki                            记忆 Wiki
┌──────────────────┐               ┌──────────────────┐
│ SESSION-X        │               │ MEMORY-Y         │
│                  │               │                  │
│ 产生的记忆:      │──────────────→│ 来源会话:        │
│   - MEMORY-Y     │               │   - SESSION-X    │
│   - MEMORY-Z     │               │                  │
└──────────────────┘               └──────────────────┘
```

**实现**：
- 会话节点的 `## 产生的记忆` 字段列出该会话中创建的所有记忆
- 记忆文件的 `related_sessions` 元数据字段列出其来源会话

成本：每个方向一行（<50 tokens）。收益：从知识条目可以追溯到产生它的对话，从对话可以追溯到其中写入的记忆——形成完整的 provenance chain。

## B.6 维护任务扩展

### 日检新增
- 检查 MEMORY.md 中是否有记忆超过 90 天未被引用但仍在热索引中 → 标记 #warm
- 检查 memory/archive/ 中是否有被 Scholar 显式引用的记忆 → 标记为复活候选

### 周检新增
- 计算所有记忆的修正排名（引用次数 × 半衰期衰减），输出降冷候选列表
- 扫描记忆内容，检测是否有语义高度重叠的记忆 → 合并候选
- 检测是否有反馈记忆已被系统默认行为覆盖（如"保留完整上下文"在系统已实现后）→ 降冷候选
- 更新记忆线程

## B.7 与参考设计的对比

参考设计的 `preserve:true` 标记在记忆系统中有了更自然的实现——不是二元的"保护/不保护"，而是通过低 τ 系数（极慢衰减）来表达"这条记忆不应该被降冷"。用户的角色定义、核心偏好——这些在本质上就是 `preserve` 的，但不需要显式标记。

## B.8 实施优先级

记忆 Wiki 编目系统的实施比对话 Wiki 更简单（单条记忆文件本来就小，不需要"节点 vs Transcript"的两层分离），但收益同样显著（启动时记忆相关 token 从 O(n) 降为 O(log n)）。

**Phase 1（即刻）**：
1. 增强 MEMORY.md 的一行格式（加标签 + 状态 + 引用计数）
2. 为现有 20 条记忆补充元数据
3. 创建 memory/archive/ 目录和 archive/INDEX.md

**Phase 2（Phase 1 后）**：
1. 实现基于排名的记忆降冷自动化（周检）
2. 创建初始记忆线程
