# 分形 Wiki 编目：全文件系统审视

> 配套于 `SYSTEM-DESIGN-v3.0.md`、`CONVERSATION-WIKI-DESIGN.md`、`MEMORY-WIKI-DESIGN.md`
> 核心命题：Wiki 编目（Registry → Thread → Node）不是会话/记忆的专利——它是任何随时间积累的文件类型的通用架构模式。三层结构足以覆盖 ~27 倍的文件规模增长。

---

## C.1 分形模式的定义

前两份设计文档在不知情的情况下各自实现了同一个模式：

| 子系统 | Registry（L1） | Thread（L2） | Node（L3） |
|--------|--------------|-------------|-----------|
| **对话** | `conversations/INDEX.md` | `conversations/threads/*.md` | `conversations/nodes/*.md` |
| **记忆** | `memory/MEMORY.md` | `memory/threads/*.md` | `memory/{type}/*.md` |
| **知识** | `tools/INDEX.md` | 主题分类 + TAGS.md | `knowledge/2026/05.md` 中的单条 KNID |

这不是巧合——这是在三个不同的子系统上独立发现了**同一个分形结构**：

```
┌──────────────────────────────────────────────────────┐
│  Registry (L1)                                       │
│  启动时加载 | 每行一条 | 总 <2K tokens               │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐                │
│  │ Thread A│ │ Thread B│ │ Thread C│   ← 按需加载   │
│  │ ~1K tok │ │ ~1K tok │ │ ~1K tok │                │
│  │ ┌─────┐ │ │ ┌─────┐ │ │         │                │
│  │ │Node │ │ │ │Node │ │ │  ...    │   ← 按需加载   │
│  │ │Node │ │ │ │Node │ │ │         │                │
│  │ │Node │ │ │ └─────┘ │ │         │                │
│  │ └─────┘ │ └─────────┘ └─────────┘                │
│  └─────────┘                                        │
└──────────────────────────────────────────────────────┘
```

**分形的含义**：同一个结构在不同的尺度上重复。Registry 是自己层级的 Node 的目录；Thread 是横切 Registry 的聚合；Node 是原子单元。

**3×3×3 ≈ 27 的含义**：Registry 本身占用 ~2K tokens。它指向的每个 Thread 展开 ~1K tokens。每个 Thread 指向 ~3-10 个 Node（每个 ~500 tokens）。三层压缩使得：如果所有 Node 平铺展开需要 ~27K tokens，经由 Thread → Registry 两层压缩后，启动时只需 ~2K tokens。

## C.3 尚未覆盖的文件类型：详细设计

### C.3.1 每日分析报告（`tools/analysis/daily/`）

**当前状态**：1 个文件（`2026-05-28.md`，~100 行），无人关注。
**增长预测**：365 个/年。一年后 365 个文件。三年后 >1,000 个文件。
**访问模式**：绝大多数不再被访问——周报已经吸收了它们的精华。只有追溯特定日期时才需要原文。

**三层结构**：

```
tools/analysis/daily/
├── INDEX.md                    # L1: Registry
│                               # 每行: 文件名 | 日期 | 状态标签 | 关键发现（15字）
│                               # 按月份分节
│                               # 近 30 天标记 #hot，31-90 天 #warm，>90 天 #cold
├── summaries/                  # L2: 月度聚合（Thread 等价物）
│   ├── 2026-05-summary.md      # 5 月的所有日报的聚合（<1K tokens）
│   └── 2026-06-summary.md
├── 2026/
│   ├── 05/
│   │   ├── 2026-05-28.md       # L3: Node（单日报告全文）
│   │   └── ...
│   └── 06/
└── archive/                    # 冷存储：>180 天的日报原文
    └── INDEX.md                # 冷报告的注册表
```

**关键设计决策**：月度总结（L2）是日报的"退休仪式"。一个月的 30 份日报 → 被聚合为 1 份月度总结。此后，日报原文进入冷存储，只有月度总结保留在热索引中。这实现了 ~30× 压缩。

**生成时机**：每月 1 日自动运行（或作为周检的一部分）。

### C.3.2 每周分析报告（`tools/analysis/weekly/`）

与日报同理，但聚合层级是季度（13 周 → 1 份季度报告）。

```
tools/analysis/weekly/
├── INDEX.md                    # L1: Registry
├── summaries/                  # L2: 季度聚合
│   └── 2026-Q2-summary.md
├── 2026/
│   ├── 2026-W22-analysis.md    # L3: Node
│   └── ...
└── archive/
```

### C.3.3 审计日志

**当前状态**：尚未创建。
**增长预测**：每次提取/consolidation/策略变更 → +1 行。保守估计 ~50 行/周，2,600 行/年。
**关键约束**：日志的每一行都有审计价值，不能删除。但 99% 的行永远不会被回溯。

**三层结构**：

```
tools/audit/
├── INDEX.md                    # L1: 变更摘要（每月一行）
│                               # "2026-05: 3 次提取, 1 次 consolidation, 0 次策略变更"
├── digests/                    # L2: 月度摘要
│   └── 2026-05-digest.md       # 5 月变更的类型、文件、KNID 清单（<1K tokens）
└── logs/                       # L3: 原始日志（冷存储）
    └── 2026-05-audit.log       # 逐行完整日志
```

**生成时机**：每日维护任务滚动写入当月的原始日志。每月 1 日，生成上月的 digest 并将原始日志移入冷存储。

### C.3.4 work/ 草稿

**当前状态**：`work/2026/05.md` 中有 3 条待处理草稿。
**已有结构**：按月分文件——这是一个自然的 L2 层（月份作为 Thread）。

**缺什么**：L1 Registry——一个 `work/INDEX.md`，给出"当前有哪些草稿、它们的状态、它们阻塞了什么"。

```
work/
├── INDEX.md                    # L1: 草稿注册表（新）
│                               # 每条草稿一行，标记 #pending / #blocked / #ready-for-review
├── 2026/
│   ├── 05.md                   # L2: 月度草稿文件（已有）
│   └── 06.md
└── archive/                    # 冷存储：已晋升或被废弃的旧草稿
```

**不需要 Thread 层**——月度文件已经是自然的聚合单元。这是分形原则的一个变体：当已有的分组逻辑（如按月）已经提供了足够的聚合，就不需要额外引入 Thread 层。

## C.4 不需要分形的文件类型（及原因）

| 文件类型 | 不需要分形的原因 |
|---------|---------------|
| **CONSTITUTION.md** | 受设计约束——它的膨胀是 SKILL.md 拆分要解决的问题，不是分形编目要解决的问题 |
| **CACHE.md** | 固定格式、固定长度（3 行），永不增长 |
| **TAGS.md** | 随知识条目增长但规模有上限（标签数量收敛于领域词汇量），且每次周检重建 |
| **GRAPH.md** | 每次周检重建，始终反映当前知识库的状态快照 |
| **SKILL.md 及其拆分后的子文件** | 受 steipete 原子解耦原则约束——如果它们膨胀了，说明拆得不够细，而非需要分形 |
| **memory/MEMORY.md** | 它本身就是记忆子系统的 L1 Registry——已经在分形结构中了 |

## C.5 分形普适性的边界

分层形编目不是一个"每个文件都需要的银弹"。判断一个文件类型是否需要分形，有且只有三个条件：

1. **该类型的实例数量随时间线性增长**（或更快）
2. **单个实例在创建后，其访问频率随时间的衰减显著**（大多数实例最终不被访问）
3. **实例之间有自然的聚合维度**（时间/主题/类型）——没有聚合维度的碎片集合同样不适合分形

反例：
- 一篇正在写作的论文草稿：只有一个实例，不满足条件 1。不需要分形。
- 一组 API 密钥：数量固定，不随时间增长。不需要分形。
- 一个随机命名的截图文件夹：没有自然的聚合维度。需要的是命名规范，不是分形。

## C.7 统一命名约定

为避免每个子系统独立发明自己的术语，采纳统一的命名约定：

| 层级 | 标准名称 | 文件名约定 | 加载时机 |
|------|---------|----------|---------|
| **L1** | **Registry** | `INDEX.md` | 启动时 / 子系统首次访问时 |
| **L2** | **Thread**（有横切聚合时）或 **Collection**（纯时间聚合时） | `*-summary.md` 或 `*-thread.md` | 当对应主题被涉及时 |
| **L3** | **Node** | 原始文件名 | 当被显式引用或搜索命中时 |
| **冷存储** | **Archive** | `archive/INDEX.md` + 原始文件 | 仅在 Scholar 显式要求时 |

统一命名的价值：当一个新会话启动，系统知道"找 `INDEX.md` → 它是这个子系统的 Registry → 从 Registry 导航到 Thread → 从 Thread 导航到 Node"。无论进入哪个子系统，心智模型一致。
