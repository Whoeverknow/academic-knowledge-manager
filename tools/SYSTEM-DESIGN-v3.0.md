# 系统架构重设计 v3.0 · 草案

> 基于 2026-05-30 对话的完整讨论脉络
> 从"academic-knowledge-manager SKILL.md 膨胀"到"系统级上下文预算架构"
> 本文件是设计文档，不是宪法——宪法将从中提取，但这两者是分离的。

---

## 第一章：问题诊断

### 1.1 触发事件

当前 `academic-knowledge-manager` SKILL.md 已膨胀至 >540 行（仅 CONSTITUTION.md），且仍在以单向阀门方式增长：每发现一个 edge case → 加一条规则，每引入一个功能 → 加一套指令，每经历一次对话污染 → 加一道防护栏。没有自然的规则淘汰机制。

### 1.2 但这不是 SKILL.md 的问题——是系统架构的问题

深入诊断后，我们识别出两个层面的问题，其严重性有数量级差异：

**表面问题**：SKILL.md 把三类变化频率不同的内容混在一个平面文件里：

| 类别 | 内容 | 变化频率 |
|------|------|---------|
| 宪法/硬规则 | KNID 格式、来源标准、不可变原则 | 几乎不变 |
| 工作流/流程 | 提取步骤、consolidation 步骤、目录结构 | 低频修订 |
| 启发式/策略 | 追问即信号映射表、偏差缓解规则、边界处理 | 持续演进 |

它们的修订周期差了两个数量级，捆在一起是当前膨胀的根源。

**深层问题**：每个会话启动时，多个子系统独立加载各自的静态内容进入上下文——记忆文件、所有已启用的 SKILL.md、知识库索引、会话模板——彼此不知道对方的存在。任意一个子系统膨胀到临界点，整体上下文预算就破了。这正是用户在过往对话中已经触发的"上下文超限"问题。

### 1.3 核心矛盾的精确定义

> **给定"上下文预算是有限且共享的"，如何设计一个由多个子系统（知识库、记忆、skills、历史会话）组成的系统，使得：**
> - **每个子系统都有明确的上下文预算上限**
> - **没有一个子系统能独占地膨胀到挤掉其他子系统**
> - **系统整体可以在预算内运行，而非依赖用户手动管理**

这不是单个 skill 的策略优化问题——这是跨子系统的架构宪法问题。

### 1.4 为什么现有机制不足以解决

| 现有机制 | 为什么不够 |
|---------|-----------|
| SKILL.md 的 amendment 流程 (Art. IX) | 只能修改内容，不能删除；旧版本归档但等效规则只增不减 |
| 每日自动回顾 (VIII.5) | 只检查知识条目，不检查系统本身的荷载 |
| 状态缓存 (VIII.1 §5) | 避免重复读取文件，但不解决启动时的上下文预加载成本 |
| baseline/ 存档 | 保存历史版本，但历史版本本身也需要存储和认知 |

没有一个机制在问：**"这些规则是否需要在此会话中全部存在于上下文里？"**

## 第二章：设计哲学

### 2.1 steipete 元原则：上下文即成本，原子即美德

在五项具体原则之上，有一条元原则来自 steipete 的 Skill 设计思想，贯穿整个架构：

> **每一个 token 进入上下文，都必须为自己辩护。** 不能为自己的存在提供理由的规则、描述、模板，就是浪费。

这个元原则的两个直接推论：

**推论一：原子解耦。** 一个 Skill 做一件事，且只做一件事。大 Skill 不是"功能更多"——是"浪费更密集"。如果 `academic-knowledge-manager` 的宪法和工作流和策略在 80% 的调用中只有 20% 被用到，那么它就应该被拆成三个独立的 Skill，各自在被需要时加载。

**推论二：渐进式披露。** 启动时只加载注册表——名称 + 一行描述。调用时才展开指令。这与预加载模型有本质区别：预加载是为"用户可能会问什么"买保险，渐进式披露是为"用户实际问了什么"付费。

### 2.2 五项核心原则

**原则一：启动集最小化**

每个会话开始前，系统必须回答：没有任何用户输入的前提下，最少需要加载什么才能保持运作？

当前违反此原则的：所有 SKILL.md 全文加载、所有记忆文件全文加载。大多数会话根本不需要它们全部。

**原则二：按需加载，而非预加载**

引用应该像 `#include` 而不是 `@import`——只在引用处生效。一个会话只用 `academic-knowledge-manager`，就不应加载 `research-writing-skill` 的任何一行。一个讨论哲学的会话，就不应加载提取流程的详细步骤。

**原则三：预算作为宪法条款**

每个子系统（记忆、知识库索引、skill 规则集、计划上下文）应有明确的上下文预算上限，以 token 计。宪法应规定：
- 总启动预算上限
- 每个子系统的分配上限
- 超额时的优先级规则（哪个子系统先降级）

没有预算上限，任何"小就是美"的设计最终都会膨胀。

**原则四：知识操作和元操作分离**

提取一条知识（知识操作）和更新索引/图/标签（元操作）应由不同的机制触发。前者是实时的，后者可以是批量的、延迟的。两者混在同一个 SKILL.md 工作流中导致规则复杂度相互嵌套。

具体而言：INDEX.md 更新、GRAPH.md 重建、TAGS.md 同步——这些应该在 maintenance 周期中执行，而不是在每次提取后实时执行。

**原则五：遗忘机制是架构的一部分，而非事后补救**

每个知识条目的生命周期应该自然包含"创建 → 活跃 → 归档 → 遗忘"四个阶段。遗忘不是"发现问题后去降冷"，而是**每个条目在创建时就预置了降冷条件**。

对应到规则层面：每条启发式策略应有"失效条件"——在什么情况下这条策略不再适用。没有失效条件的策略会永远留在系统中。

### 2.2 设计哲学的综合表述

这些原则共同指向同一组假设：

- **存储不是瓶颈，认知带宽才是**。硬盘可以存海量文件，但上下文窗口、注意力、推理深度极其有限。
- **系统复杂度应在设计阶段消化，而非运行时补丁式增长**。每一条后加的规则都证明设计不足，但每一条规则都有成本——而且不会自行退役。
- **不设上限的优化等于没有优化**。任何子系统如果不设预算上限，它的优化永远在追逐它的膨胀。
- **透明的规则需要透明的规则管理**。如果一个系统声称"可审计、可逆"，那么修改系统本身的规则也必须是可审计、可逆的。

## 第三章：系统架构规划

### 3.1 子系统划分与预算分配

以下是将上下文预算作为一个可计量的架构参数，对当前所有子系统所做的首次全局审视：

```
┌─────────────────────────────────────────────────────────┐
│  启动集（每次会话初始化时自动加载，不可躲避）             │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐       │
│  │ 核心指令     │ │ 活跃角色/   │ │ 系统级宪法  │       │
│  │ (system     │ │ 上下文标记   │ │ (精简版,    │       │
│  │  prompt中   │ │ (memory     │ │  <500字)    │       │
│  │  不可移除)  │ │  index)     │ │             │       │
│  └─────────────┘ └─────────────┘ └─────────────┘       │
│      ~3K tokens       ~1K tokens        <1K tokens     │
└─────────────────────────────────────────────────────────┘
                         │
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ Skill 定义  │ │ 知识库索引  │ │ 记忆文件    │
│ (惰性加载)  │ │ (惰性加载)  │ │ (惰性加载)  │
│             │ │             │ │             │
│ 用户在对话  │ │ 仅当用户    │ │ 仅当引用    │
│ 中调用时才  │ │ 涉及学术    │ │ 到具体主题  │
│ 展开完整    │ │ 知识管理    │ │ 时才加载    │
│ 指令        │ │ 时才加载    │ │ 对应文件    │
│             │ │ INDEX/GRAPH │ │             │
└─────────────┘ └─────────────┘ └─────────────┘
```

**关键变化**：
- **Skill 不再预加载全文**。当前 SKILL.md 是 >540 行的单一文件，在新架构下只有一个精简的注册表项（<200 tokens），只在用户调用时展开完整的工作流/宪法/策略。
- **知识库索引不是启动时加载的**。INDEX.md 当前 >90 行并持续增长，在新架构下仅在知识操作需要时才读入。
- **记忆文件按需访问**。当前 MEMORY.md 是全文加载的（当前很小，但会增长），在新架构下索引和正文分离，索引是启动的一部分，正文按需加载。

### 3.2 SKILL.md 的三向拆分

这是第一个具体的、可以立刻执行的重构行动：

```
当前：
SKILL.md (>540行，三合一)
         │
         ▼
重构后：
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ CONSTITUTION.md │  │ WORKFLOW.md     │  │ STRATEGY.md     │
│                 │  │                 │  │                 │
│ 不可变硬规则     │  │ 固定操作流程     │  │ 启发式与策略     │
│                 │  │                 │  │                 │
│ · KNID格式      │  │ · 提取步骤      │  │ · 追问即信号    │
│ · 来源标准      │  │ · consolidation │  │ · 偏差缓解      │
│ · 伦理准则      │  │ · 目录结构      │  │ · Edge case处理 │
│                 │  │ · 维护计划      │  │                 │
│                 │  │                 │  │                 │
│ 修订：低频      │  │ 修订：低频      │  │ 修订：持续      │
│ 需amendment流程 │  │ 需amendment     │  │ 可快速迭代      │
│ baseline/备份   │  │ baseline/备份   │  │ 有失效条件      │
└─────────────────┘  └─────────────────┘  └─────────────────┘
```

**三个文件的特征与生命周期**：

| 维度 | CONSTITUTION.md | WORKFLOW.md | STRATEGY.md |
|------|----------------|-------------|-------------|
| 何时加载 | 仅在调用该 skill 时 | 与宪法同步加载 | 仅在需要该特定策略时 |
| 修订门槛 | 高（需明确 Scholar 指令 + baseline 备份） | 中（需 Scholar 确认） | 低（可从使用中自动调整，但需记录） |
| 膨胀风险 | 中（硬规则有限） | 低（流程有限） | **高（持续演进）** |
| 是否有失效机制 | 无需（规则本身是常驻真理） | 无需（流程相对固定） | **必须有**——每条策略标注"在什么条件下失效" |
| 上下文份额 | ~2-3K tokens | ~1-2K tokens | ~1-2K tokens（高频部分）+ 按需扩展 |

**STRATEGY.md 的特殊性**：这是唯一会持续增长的部分。必须内置自限机制：
- 每条策略标注 `**激活条件**`（在什么上下文中生效）和 `**失效条件**`（在什么情况下退役）
- 总量达到上限时，最低被引用度的策略自动降冷到冷索引
- 每月自动审计：哪些策略过去 30 天未被触发？→ 降冷

### 3.3 知识条目的生命周期（基于齐夫定律 + 文献半衰期）

当前模型是二态的：work/（草稿）→ knowledge/（已发布）。但"已发布"是一个终端状态——一旦发布，条目永不改变。需要引入基于统计规律而非固定阈值的降冷机制。

**3.3.1 齐夫定律在时间维度的扩展**

齐夫定律（Zipf's Law）的原始形式是：词频排名第 $n$ 的词，其频率约等于第 1 名的 $1/n$。扩展到知识条目的访问模式：

> **在任何足够长的时间窗口中，对知识条目的引用次数近似服从幂律分布。** 排名第 1 的条目被引用的次数远多于排名第 10 的，排名第 100 的基本上只在冷搜索中被触及。

这意味着：

- **不能把降冷阈值设为固定天数（如"180 天未引用 → 归档"）。** 幂律分布下，"被引用"和"未被引用"之间不存在一个干净的时间分割点。有些条目天生低频但永远重要（如理论框架、定义性条目），有些条目高频但迅速过时（如工具教程、数据源）。
- **真正有效的分割维度是引用排名，而不是时间间隔。** 降冷应该是"引用排名跌出热索引容量上限"，而不是"距最近一次引用超过 X 天"。
- **热索引的规模不由时间决定，由预算决定。** 热索引大小设为 $K$（如 $K=30$ 条），始终保留引用排名最高的 $K$ 条。新条目进入时可能挤掉旧条目——除非旧条目有持续性引用。

**3.3.2 文献半衰期：时间仍然重要，但不是作为阈值**

文献计量学中的"半衰期"（half-life）指：引用该文献的活跃期过了一半的时间点。不同学科/类型的半衰期差异很大：

| 知识类型 | 典型半衰期 | 降冷含义 |
|---------|----------|---------|
| 理论框架 / 数学基础（如 Ramsey 模型） | **极长**（数十年） | 即使引用频率低，也应在热索引中保留更久——理论半衰期极长 |
| 方法论文献（如 GTAP v7 手册） | **中等**（5-10 年） | 被新版本取代后快速降冷；方法论引用的价值随时间衰减 |
| 实证研究 / 数据源（如 CWON 数据集） | **中短**（3-5 年） | 数据版本更新快；旧数据的参考价值递减 |
| 工具教程 / 代码（如 MAgPIE 安装指南） | **短**（1-3 年） | 软件版本更替使其快速过时 |
| 新闻 / 当前事件 | **极短**（<1 年） | 几乎不进入知识库 |

**半衰期修正齐夫排名**：在计算引用排名时，引入一个半衰期衰减因子。一个分类为"理论框架"的条目，即使引用频率低，其"有效排名"也会被上调——因为它的知识半衰期更长，不应和"工具教程"按同样的速度降冷。

简化公式（不需要精确实现，但作为排序直觉）：

$$\text{effective\_rank} = \text{raw\_rank} \times \frac{1}{1 + \alpha \cdot \text{age\_in\_months}}$$

其中 $\alpha$ 是衰减系数，由条目的类型标签决定：$t$-concept $\ll$ $t$-method < $t$-tool < $t$-data < $t$-case。

**3.3.3 修正后的四态生命周期**

```
┌─────────┐    引用排名在前K     ┌─────────┐    引用排名跌出K    ┌─────────┐
│  创建    │ ──────────────────→ │  活跃    │ ────────────────→ │  归档    │
│ (work/) │                     │ (热索引) │                    │ (温索引) │
└─────────┘                     └─────────┘                    └─────────┘
                                      ↑                              │
                                      │     被显式引用后复活          │
                                      │                              │
                                      │                    引用+半衰期评分跌出温索引阈值
                                      │                              │
                                      │                              ▼
                                      │                        ┌─────────┐
                                      └────────────────────────│  退役    │
                                                                │ (冷索引) │
                                                                └─────────┘
                                                                      │
                                                                      │  仅保留墓碑摘要
                                                                      ▼
                                                                  [墓碑]
```

**过渡条件（排序驱动，非时间驱动）**：

| 过渡 | 触发条件 |
|------|---------|
| 创建 → 活跃 | 条目在 daily consolidation 中被 review → 晋升到 knowledge/，进入热索引竞争池 |
| 活跃 → 归档 | **热索引容量 $K$ 已满，且本条目的修正排名（考虑半衰期）跌出前 $K$** |
| 归档 → 退役 | **温索引容量已满，且排名跌出温索引阈值**（通常在归档后长期未引用 + 半衰期衰减充分） |
| 任意 → 活跃 | Scholar 在对话中显式引用该条目 → 排名跃升，直接回到热索引 |

**关键差异**：
- 不是"180 天未引用 → 归档"，而是"热索引有 $K$ 个位置，你的排名没进前 $K$ → 归档"
- 一个 5 年前的理论条目如果每次都出现在 Scholar 的讨论中，它永远不会归档——因为它的引用排名保持在前 $K$
- 一个上月刚创建的新闻类条目可能快速跌出——因为它的半衰期系数让它排名衰减极快
- $K$ 本身不是魔数——它等于分配给知识库索引的上下文预算除以单条索引的平均 token 数

**3.3.4 内存（memory）中的条目同理**

这条原理不限于知识库。记忆文件中的条目——用户偏好、项目记录、工作风格——也服从类似的分布。高频激活的记忆留在热记忆中，低频的降冷。**一个 6 个月前写下的项目备忘，如果之后从未被提起，就应该在记忆检索的竞争中自然下沉。**

### 3.5 检索策略：Wiki 结构导航 > 搜索引擎

参考设计中构想了一个完整的检索层——`search`、`expand_search`、`schedule_offline`、向量索引、倒排索引。这是过度设计。

**我们已有的搜索基础设施远超参考设想：**

| 现有机制 | 等价于 | 作用 |
|---------|-------|------|
| INDEX.md 按优先级/主题排序 | 分类索引（Category Index） | 按意图定位 |
| 每个条目的 `**Related**` 字段 | Wiki 风格的交叉引用 | 从已知条目导航到相关条目 |
| TAGS.md 标签关联图 | 概念网络 | 从概念出发找到所有相关条目 |
| GRAPH.md 概念关系图 | 可视化导航 | 全局结构一览 |
| 每个条目的英文学术标题 | 精确匹配关键词 | 直接检索 |

这些加在一起，就是一个 Wiki 风格的导航系统——从入口点出发，通过交叉引用和分类浏览找到目标。这是 Wikipedia 的模式：绝大多数页面是通过"链接→链接"找到的，不是通过搜索框。

**我们应该做的是增强这个模式，而不是在它上面盖一个搜索引擎：**

1. **入口页面（Portal）**：INDEX.md 的增强版——不只是分类列表，而是带有入站链接计数的"热门入口"
2. **消歧义页面**：当一个关键词可能指向多个条目时，创建消歧义页面（如"碳预算可能指物理碳预算或政策碳预算"）
3. **Category 页面**：每个标签自动汇总其下所有条目——类似 Wikipedia 的 Category 页面，但由 TAGS.md 驱动
4. **"从这里出发"的推荐链接**：在每个条目的底部，根据共引关系和标签重叠度，推荐"下一个可能相关的条目"

**什么时候需要搜索引擎？**

当条目数增长到 ~200+，且 Wiki 链接覆盖率不足时——也就是当存在大量未被链接覆盖的冷条目。但这个阈值不是我们现在需要担心的，而且即使到了那一天，搜索引擎也应该尝试"用现有链接结构做 PageRank 风格的权重排序"，而非引入一个外部的向量数据库。

成本对比：
- 构建向量搜索引擎：引入新依赖、新索引文件、新 token 消耗、新维护流程
- 增强 Wiki 导航：扩大已有的 INDEX / Related / Tags / Graph 的覆盖率和质量

后者只消耗我们已经有的东西。

### 3.6 审计与可逆性机制

当前系统已有的审计/可逆机制：
- `baseline/` 存档（宪法每次修订前备份旧版本）
- `CACHE.md` 状态记录
- 每日回顾日志

**缺失的**：

1. **每次提取操作应产生 audit 条目**：谁请求的（Scholar）、何时、提取精度（完整/部分）、来源文件、写入哪个 work/ 文件
2. **每次 consolidation 应产生变更记录**：哪些条目被晋升、哪些被合并、KNID 是否被退役
3. **每次策略变更应记录**：STRATEGY.md 的任何修改都应像宪法修订一样进入 baseline/
4. **墓碑机制**：当一个条目被融合（两个条目合并为一个），旧的 KNID 应留下墓碑（原位置的一个单行标记：`> 此条目已合并至 [[新KNID]]，原因：{为什么合并}，日期：{日期}`）

**成本极低**：每条审计日志 <100 字节，1000 条日志只有 100KB。

## 第四章：与参考设计的批判性对比

用户提供的参考设计（"cognitive_index_manager"）包含了一些有价值的洞见，但也存在系统性的错位：

### 4.1 被吸收的洞见（移植到我们的架构）

| 参考洞见 | 在我们架构中的位置 | 移植后的形态 |
|---------|-------------------|------------|
| "认知资源是瓶颈" | 已转化为 steipete 元原则 + 原则一（启动集最小化）+ 原则三（预算上限） | 不仅是口号——每个子系统都有 token 硬上限 |
| 热/冷分离 | 已转化为知识条目生命周期（§3.3），粒度从文件改为条目 | **进一步修正**：不是固定时间阈值，是齐夫排名驱动的自然分层 |
| 可审计遗忘 | 已转化为审计机制（§3.6），增加了墓碑和变更记录 | 维持 |
| 维护任务异步化 | 已转化为原则四（知识操作与元操作分离） | 维持 |
| 不轻易删除，只降冷 | 已转化为哲学核心 + 四态生命周期 | 降冷速度不由时间决定，由引用排名和半衰期决定 |

### 4.2 被拒绝的设计（及拒绝理由）

| 参考设计 | 拒绝理由 |
|---------|---------|
| 500MB 热索引阈值 | 错误的度量单位。我们的瓶颈是上下文 token（~200K），不是磁盘 RAM。阈值应以 token 计，以子系统预算方式分配。 |
| `preserve:true` 标记 | 二元标记粒度太粗。需要状态机（创建→活跃→归档→退役）而非标志位。 |
| 文件级的操作粒度 | 我们的操作粒度是知识条目（KNID），不是文件。一个文件可能包含多条条目，一条条目可能需要被独立降冷。 |
| 空白检测 + 语义合并 | 方向正确但在我们场景中的问题倒过来了——我们的需求不是去重，而是边界不清的条目的重新划分。 |
| 异步化模型（文件系统 I/O） | 我们的操作更多是认知密集型（LLM 调用），异步化不能减少总 token 消耗。真正的杠杆在"不在启动时加载不需要的东西"。 |
| 七个 action 定义（search/expand_search/schedule_offline...） | 过度设计了检索层。知识库应有的搜索模式是 Wiki 风格的链接导航（Related + Tags + Category + Portal），而非外部搜索引擎。详见 §3.5。 |

### 4.3 参考自身的设计悖论

参考声称"认知资源是瓶颈"，但它给出的方案本身包含 ~3,000+ 字的指令、7 个 action 定义、6 个宪法条款、若干 JSON schema。加载这个参考本身就在消耗认知资源——这是一个**自反悖论**。

我们的设计必须避免这个陷阱：架构本身的描述不应成为上下文预算的最大消耗者。

3. **自动降冷自动化** — 周期性的归档/降冷检查，含 Scholar 确认流程
4. **跨会话知识复用** — 在多个会话中共享对知识库的检索结果，避免每次从头加载

## 第六章：已解决与仍待确认的问题

### 6.1 已解决（经 2026-05-30 讨论确认）

**Q1：Token 预算的具体数值？**

**已解决**。不需要一个全局魔数。预算由 steipete 元原则决定：**启动时只加载 Skill 注册表（名称 + 一行描述），调用时展开指令。** 具体数值是此原则的实施结果，而非先验参数。

具体实施：
- 启动集：系统 prompt（不可控）+ 记忆注册表 + Skill 注册表 + 精简版宪法索引（估 <5K tokens）
- 每个被调用的 Skill 展开后：根据 Skill 的预算上限自行控制（如 `academic-knowledge-manager` 的启动指令不超过 2K tokens）
- 如果一个 Skill 的指令超过预算 → 它需要被拆成更小的原子 Skill

**Q2：降冷的速度应该是多少？**

**已解决**。不是固定时间，是齐夫排名驱动的自然竞争。关键参数：

| 参数 | 含义 | 初始值建议 |
|------|------|----------|
| $K_\text{hot}$ | 热索引容量（条目数） | ~30-50（取决于单条索引平均 token 数 × 预算上限） |
| $\alpha_\text{concept}$ | 理论/概念的半衰期衰减系数 | 极低（~0.001/月） |
| $\alpha_\text{method}$ | 方法/工具的衰减系数 | 低（~0.01/月） |
| $\alpha_\text{data}$ | 数据源的衰减系数 | 中（~0.03/月） |
| 排名计算方法 | 引用次数 × (1 / (1 + α × age)) | 简单加权，可后期优化 |

### 6.2 仍待确认

1. **STRATEGY.md 是否允许从使用中自动调整？** 还是所有策略变更都需要 Scholar 确认？（自动调整加快迭代但增加不可控风险）
2. **跨 session transcript 的检索**——当用户需要在过往对话中找东西时，如何避免每次都要加载整个旧会话？
   → **已解决**：通过会话 Wiki 编目系统（详见 `tools/CONVERSATION-WIKI-DESIGN.md`）。新会话加载会话节点（~500 tokens）而非完整 Transcript（20K-100K tokens）。50 个跨会话场景中，48 个在 <3K tokens 内解决。
3. **Skill 的原子化应该推进到多细的粒度？** `academic-knowledge-manager` 拆成 Constitution / Workflow / Strategy 是否足够，还是应该进一步拆？（例如：Strategy 中的"追问即信号"逻辑是否该独立成一个微型 Skill？）
